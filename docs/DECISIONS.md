(for example, which ROS message type to use). Bryan can veto any entry:
edit the line or add "VETOED:" and the next agent run will redo that part.

| 2026-11-16 | Rotation in place (angular != 0 with abs(linear) < 0.02, no arm action) is refused when the sonar on the side being swung into (CCW = left, CW = right) reads below `side_clearance` (0.20 m, working value, TODO: Bryan to tune). In SEARCH the spin direction flips if the other side is clear and the front is not blocked; avoidance turns are zeroed instead of flipped so the robot never turns back into the front obstacle. Both sides close: stands still (SEARCH has no timeout for this; item 15/22 add stale/validity handling) | Skid-steer corners swing sideways; simple and testable | active |

| 2026-11-16 | Bring-up config: `robot.yaml` lists EVERY declared parameter of drive, ultrasonic, arm, gps_imu, detector and behavior (a test fails if a node declares one the yaml lacks, if the yaml has an unknown one, or if an int/float type differs from the node default, which ROS would reject). Top-level keys stay the launch node names (`ultrasonic:` = sonar subsystem). Per-subsystem launch files call `bringup_util.subsystem_launch`; unset markers (-1 pin, 0 number, empty string) are reported by `config_logic.unset_message` | One file for Bryan to edit; reuses existing idle-with-warning behavior of the nodes | active |
| 2026-11-16 | `hardware_check` console script (`hardware_check.py` + pure `hardware_check_logic.py`): per subsystem PASS (all set, no pin problems) / FAIL (unset, invalid or conflicting) / SKIP (nothing filled in yet); exit code 1 on any FAIL | Lets Bryan fill in `robot.yaml` part by part and re-run; SKIP for unassembled parts so the full run is not all red | active |
| 2026-11-16 | Valid pins = BCM 2..27 (Pi 5 header; GPIO0/1 are the HAT ID EEPROM). Pins are checked for duplicates across drive and sonar, and against I2C (GPIO2/3) and GPS UART (GPIO14/15) when the IMU/GPS is configured. A sonar with both pins -1 counts as unused; only one of the two set is FAIL | Header facts, not robot facts. Does not decide the pin budget (blocked on Bryan, item 23) | active |
| 2026-11-16 | Calibration helpers: pure maths in `calibration_logic.py`, thin wrappers in `calibrate.py` exposed as 5 console scripts. Encoders are read directly with gpiozero from `drive.enc_*_pins` (drive node must be stopped) because the drive node publishes no raw ticks and must not be extended; wheel radius scales by measured/odom distance, track width by odom/measured yaw; pick zone = median floor y, tolerance = max(0.05, 3 sigma of x, worst offset from centre); camera pitch is fitted by bisection from a marker on the centreline at a known distance; sonar_test passive check (no data / no echo / stuck) plus a hand-cover test that finds swapped sensors | Each number comes from one physical action; logic is CI-testable | active |
| 2026-11-17 | Sonar scheduling (item 15): the ultrasonic node no longer uses gpiozero `DistanceSensor` (its sensors ping on their own and cannot be serialized). It drives trig/echo with `DigitalOutputDevice`/`DigitalInputDevice` and times the echo by polling (`sonar_scheduler.measure_echo`), one sensor per tick, round-robin, `settle_gap_s` 0.06 s after each ping, `echo_timeout_s` 0.025 s. `publish_rate_hz` removed; one full round is about 0.7 s worst case (about 1.5 Hz per sensor) | HC-SR04s hear each other, so only one may fire at a time; polling resolution on a Pi is unverified (hardware test) | active |
| 2026-11-17 | Sonar validity: no echo or beyond 4 m is published as `max_range` (4.0 m, never 0 or inf); inside the 2 cm blind zone as `min_range` (0.02 m, an obstacle). Behavior treats a sensor that reported before but has been silent more than `sonar_stale_timeout` (2.0 s, local receive time) as blocked (range 0); a sensor that has never reported is treated as not installed (inf) so a partly assembled robot still runs. `calibrate sonar_test` maps range >= max_range to no echo | Keeps old inf/-inf callers working; blocked-on-silence is the safe side; never-heard stays permissive until item 22's safety stage | active |
| 2026-11-17 | Sim pickup-rate test (item 16): mission runner lives in `sim_mission.py` (own module, not in `sim_logic.py`); the arm is simulated with fixed durations (pick 2 s, deposit 1.5 s, stow 1 s, sim only) and the robot stands still while the arm works. Pass threshold 80% on open-floor and near-wall scenarios; corner scenario guarded at its current 50% baseline. | Repeatable software number toward the 80% target and a regression guard; threshold constants are not robot measurements. | active |
| 2026-11-17 | Trial logging (item 17): `TrialRecorder` (pure Python, `trial_log.py`) watches `BehaviorMachine.state` transitions; one JSON line per attempt, from SEARCH->APPROACH until it falls back or leaves DEPOSIT. Failure reasons come from a new `BehaviorMachine.reason` attribute (target_lost, approach_timeout, pick_failed, arm_timeout, deposit_failed). One file per run, `trial_log_dir` (default `~/curiosity_trials`, empty disables). Litter type is read from `litter_type`/`class_name`/`label` in `/vision/target`, else `unknown` (detector message left unchanged: detector message type is Bryan's decision). `trial_summary [files or dirs]` prints rate overall, by litter type and per run | No behavior change; JSON Lines survives power loss since each record is flushed | active |
| 2026-11-17 | Search pattern (item 18): SEARCH drives boustrophedon rows (along the start heading, stepping across) in the odometry frame, area centred on the start pose (`search_area_length/width`, default 4 x 4 m, TODO: Bryan), edge margin 0.3 m, row spacing derived from camera FOV and `search_detect_range` (1.5 m guess) with 20% overlap unless `search_row_spacing` > 0. Pose comes from `/odom` (new optional `pose=` argument of `BehaviorMachine.step`); no fresh odometry or `search_pattern: spin` keeps the old spin. Go-to-waypoint: rotate in place if heading error > 0.5 rad, else drive and steer. Obstacles: existing front stop/avoid turn; a waypoint is skipped after 10 s without progress or without clear front. Side spin-flip is disabled while the pattern is active (the stuck timer handles it) | Needs only odometry and no map; no new dependencies; spin fallback keeps a partly assembled robot working | active |
| 2026-11-17 | Detector latency (item 19): a daemon thread (`frame_grabber.FrameGrabber`) reads the camera continuously into a single-slot `LatestFrame`; the detector timer takes the newest frame at most once and older unprocessed frames are dropped. Timer period comes from `process_rate_hz` (default 10 Hz, clamped 0.5-60 Hz) instead of 1 ms. Measured FPS (2 s sliding window, `RateMeter`) is published about once a second on `/vision/fps` (`std_msgs/Float32`); the existing 30-frame log line stays. The `cv2.VideoCapture` is now `self.capture` because `self.camera` was being overwritten (the ground-projection pose was lost, so base_x/base_y would have failed) | Stale buffered frames were the latency source (RISKS.md #11); a rate cap avoids spinning the Pi at 100% when YOLO is fast; Float32 is the standard type; the rename is a bug fix | active |
| 2026-11-18 | Detection filtering (item 20): `DetectionFilter` tracks each box by nearest-neighbour matching of normalized centres (`track_match_radius` 0.10) and reports a target only when its track was seen in `confirm_frames` (3) of the last `confirm_window` (5) frames AND is seen in the current frame. Boxes under `confidence` or whose centre is inside an `ignore_regions` rectangle are dropped. Best target = smallest ground distance from `base_x/base_y` (unknown distance ranks last), ties by confidence. `ignore_regions` is a flat float list of x1,y1,x2,y2 groups (ROS params cannot nest); the default is one zero-area group meaning none. The published JSON is unchanged; the GPT fallback path is untouched | Removes single-frame flicker and self-detections of the hoop/arm; nearest litter first suits approach; costs about 2 frames of latency at 10 Hz | active |
| 2026-11-18 | Arm kinematics (item 21): planar-arm constants (link lengths, zero angles, pan axis, senses) were derived once with the branch's `extract_planar_arm` from `so101_upstream.urdf` and baked into `arm_kinematics.SO101`, so the module needs only `math`. `plan_pick_poses` tries approach angles -90, -75, -60 deg (steepest first), requires both grasp and clearance points to solve, never clamps. Pick zone x 0.35-0.56 m and y within 0.30 m of base_link; mount x 0.115 m (experimental branch, NOT this CAD), mount height 0.2155 m (STATE.md). Backend value = `joint_sign * model + joint_offset`. Arm node reads `/vision/target` (JSON `base_x/base_y`, max age `target_max_age_s` 1.5 s) and `ik_enabled` defaults to false so fixed poses stay the default until calibrated | Keeps CI testable without numpy/urdf_parser_py; honest rejection beats clamping; LeRobot calibration to model angles is unknown so it is a parameter | active |
| 2026-11-18 | Safety output stage (item 22): `SafetyStage` runs last in `behavior_node` before `cmd_vel`. Forced stops (hard stop: front sonar min < 0.12 m; any previously-reporting sonar stale or, with `safety_require_sonars` true, none ever reported; no behavior update within 0.5 s; NaN/inf command) set zero immediately, no ramp. Normal commands are clamped (0.4 m/s, 1.0 rad/s) and acceleration-limited (0.5 m/s^2, 2.0 rad/s^2, both directions); restart after a stop ramps from rest. Hard stop zeroes rotation too (literal reading of the item); 0.12 m is below `stop_distance` 0.25 so normal avoidance acts first. A 10 Hz watchdog publishes zero if the tick stalls. All limits are working values, not measured. | Matches the item; last-stage filter is independent of behavior logic. | active |
| 2026-11-20 | Package hygiene (item 26): rosdep keys chosen from import names; pip-only packages left as a comment, not rosdep keys | python3-* keys are standard rosdep names; ultralytics/smbus2/lerobot have none, so they stay pip installs. | active |
| 2026-11-22 | Pico wheel loop (item 27), OPTION, not selected: `firmware/pico_wheels` (MicroPython) runs the speed loop; ASCII line protocol with XOR checksum (`PINS`, `CFG`, `V`, `STOP`, `T` telemetry at 50 Hz, `ERR`); `pico_bridge` ROS node mirrors the drive node (`/cmd_vel` in, `/odom` out); launch argument `wheel_backend:=pi|pico`, default `pi`; pins and tuning are sent from `robot.yaml` so the Pico has no config file; Pico stops itself after `pico_cmd_timeout_s` without a command; one encoder per side like the Pi node. Pros of Pico: encoder edges are counted by a dedicated chip (no missed edges when the Pi 5 is busy, and fewer Pi pins used: see PIN_BUDGET.md), a watchdog that works even if the Pi hangs. Cons of Pico: one more board, firmware and USB cable to build and debug, 3.3 V logic and wiring to redo, extra latency from serial. Pros of Pi: nothing new to wire or flash, already written. Cons of Pi: GPIO edge counting is done by interrupts in Python, uses Pi pins. | Bryan asked for the Pico as an option; the choice between backends is his (blocked item). Code is shared-style (same control law, same parameter names) so measured values transfer. | option, not selected |
