# Design Decisions

The agent records design choices here when a TODO item leaves one open
(for example, which ROS message type to use). Bryan can veto any entry:
edit the line or add "VETOED:" and the next agent run will redo that part.

| Date | Decision | Why | Status |
|------|----------|-----|--------|
| 2026-11-13 | Detections stay as JSON in `std_msgs/String` on `/vision/target` (plus `/vision/direction`), now with a `source` field (`yolo`/`gpt4o`) | Existing consumers already use this; vision_msgs is not in the base CI image. Can migrate to `vision_msgs/Detection2DArray` later | active |
| 2026-11-13 | GPT-4o fallback is off by default (`gpt_fallback_enabled`), runs in a background thread, only when YOLO finds nothing or best conf < `gpt_fallback_low_confidence`, at most every `gpt_fallback_interval_seconds`; key only from `OPENAI_API_KEY` env var | Keeps API cost bounded and never blocks the frame loop; no secret in repo | active |
| 2026-11-13 | GPT is asked for normalized 0..1 boxes as JSON; invalid/out-of-range replies are ignored; a reply is trusted for 2x the interval | GPT bounding boxes are approximate, so reject bad data rather than steer on it | active |
| 2026-11-13 | Ultrasonics: one `sensor_msgs/Range` topic per sensor, `/ultrasonic/<name>` (names per the 2026-11-15 layout row), frame `ultrasonic_<name>`; +inf = nothing seen, -inf = too close; 3-sample median filter; reads via `gpiozero.DistanceSensor` (lgpio backend on Pi 5), imported lazily | Standard message type; gpiozero works on Pi 5 with no extra service; per-sensor topics keep nav/behavior code simple. Lives in `trash_vision` package for now so existing CI covers it. Sensor names superseded by the 2026-11-15 layout row | active (names superseded) |
| 2026-11-13 | GPIO pins are parameters `trig_pins`/`echo_pins` (8 entries each, order now front_1, front_2, rear_1, rear_2, left_1, left_2, right_1, right_2), default -1 = unused; node idles with a warning until set | Pins are unknown hardware facts; TODO: Bryan to fill in. Old front_1..4/rear_1..4 order superseded 2026-11-16 | active |
| 2026-11-13 | Drive: `drive` node in `trash_vision`; subscribes `cmd_vel` (`geometry_msgs/Twist`), publishes `odom` (`nav_msgs/Odometry`); no TF broadcast yet (tf2_ros not guaranteed in CI image; add with bringup) | Standard types; keeps CI build safe | active |
| 2026-11-13 | MDD10A driven in PWM+DIR mode via gpiozero (1 kHz PWM); per-wheel PI with feed-forward, accel slew limit, wheel-speed clamp that preserves the arc, `cmd_vel` timeout (0.5 s) stops motors | Simple, safe defaults; logic is pure Python in `drive_logic.py` so CI tests it | active |
| 2026-11-13 | Encoders decoded in software x4 quadrature from gpiozero edge callbacks (A and B both) | No extra library; fine at JGB37-520 speeds. Switch to a pigpio/lgpio hardware counter if ticks are missed | active |
| 2026-11-13 | Pins, `ticks_per_rev`, `wheel_radius_m`, `track_width_m` are parameters defaulting to unset; node idles with a warning (TODO: Bryan to fill in) | Hardware facts unknown | active |
| 2026-11-13 | Arm: `arm` node in `trash_vision`; `std_srvs/Trigger` services `arm/pick`, `arm/deposit`, `arm/stow`; publishes `arm/joint_states` (`sensor_msgs/JointState`) | Standard types, no custom interface package needed in CI. Can migrate to an action later for feedback/cancel | active |
| 2026-11-13 | Pick = fixed waypoint sequence (pre_grasp, grasp, close, lift, stow) with per-step interpolation and joint clamping; success only if gripper stopped open by `grasp_min_gap` | Simple and safe; vision-guided grasp poses can come with the behavior node. Poses are placeholder parameters (TODO: Bryan to calibrate) | active |
| 2026-11-13 | Backend is LeRobot `SO101Follower` (lazy import); empty `port` or failure to open falls back to a dry-run backend that does not move anything | CI/dev without hardware; LeRobot API may differ by version, verify on Pi | active |
| 2026-11-13 | GPS/IMU: one `gps_imu` node in `trash_vision`; publishes `sensor_msgs/NavSatFix` on `gps/fix` and `sensor_msgs/Imu` on `imu/data` | Standard types, no extra CI deps | active |
| 2026-11-13 | GPS read as NMEA over serial (pyserial, lazy import), GGA sentences only with checksum check; covariance estimated from HDOP (HDOP x 2.5 m) | Works with any NMEA GPS module, so the model need not be known | active |
| 2026-11-13 | IMU backend is a model switch `imu_model` (default "" = off); only "bno055" (I2C, NDOF fusion, smbus2 lazy import) is implemented | A concrete model is needed to read registers; BNO055 is a placeholder guess. TODO: Bryan to fill in real IMU model (add a backend if different) | active |
| 2026-11-13 | `gps_port`, `gps_baud`, `imu_model`, `imu_i2c_bus/addr` are parameters; node idles with warnings until set | Hardware facts unknown | active |
| 2026-11-14 | Behavior: `behavior` node + pure `behavior_logic.py` state machine SEARCH -> APPROACH -> PICK -> DEPOSIT -> STOW (+ RECOVER backup after 2 failed picks); reads `/vision/target` JSON and `/ultrasonic/*`, publishes `cmd_vel` and `behavior/state`, calls `arm/pick`, `arm/deposit`, `arm/stow` | Uses existing interfaces; logic testable in CI | active |
| 2026-11-14 | Behavior is disabled by default (`enabled:=false`); pick triggers when target floor-point y >= `pick_floor_y` and centered (TODO: Bryan to calibrate); front sensors assumed ordered left->right (front_1 = left, front_2 = right); deposit = `arm/deposit` (bin is on the robot); no GPS navigation, search = spin in place | Safe default; hardware facts unknown | active |
| 2026-11-14 | Obstacle avoidance: stop at `stop_distance` (0.25 m) and turn away from the closer half; linear speed ramps down between `slow_distance` (0.6 m) and stop; backup in RECOVER is blocked by rear sensors (still true with rear_1..2) | Simple reactive behavior; thresholds are tunable parameters | active |
| 2026-11-14 | Simulation is a lightweight pure-Python 2D kinematic sim (`sim` node, `sim_logic.py`) that replaces drive/ultrasonic/detector/arm (same topics/services), not Gazebo; `sim.launch.py` runs it with `behavior` enabled | Gazebo (ros_gz) is not in the CI image and cannot be tested here; this exercises the real behavior node end-to-end. Gazebo world can be added later | active |
| 2026-11-14 | `bringup.launch.py` starts drive, ultrasonic, detector, arm, gps_imu (each switchable via `use_<node>:=false`) with hardware params from `config/robot.yaml`; `behavior` always started but disabled unless `enable_behavior:=true` | One command on the Pi; unset hardware makes nodes idle instead of fail. yaml values are TODO: Bryan to fill in | active |
| 2026-11-14 | Sim camera/sensor geometry (FOV 1.2 rad, sensor bearings, floor-row model) are invented sim-only constants, not robot facts | Only for exercising logic; real values come from hardware tests | active |
| 2026-11-16 | Ground projection: `ground_projection.py` ports the REPO-REVIEW.md formula; `/vision/target` gains `base_x`/`base_y` (base_link metres, null above horizon); camera pose/FOV are `detector` params (`camera_*`) in `config/robot.yaml`, defaults from CAD V16-18 per STATE.md, not measured; no camera yaw/roll modelled | Fixes camera/arm offset (RISKS #3); additive JSON change keeps consumers working; camera VFOV 41 deg is a lens guess | active |
| 2026-11-16 | Behavior robustness: APPROACH gets `approach_timeout` (30 s) then SEARCH with `approach_cooldown` (3 s) during which detections are ignored; `/vision/target` older than `target_stale_timeout` (1 s) is dropped in the node so a dead detector cannot hold APPROACH; `arm_result` takes the action name and ignores stale replies from a state that already timed out; removed unused node fields | Applies QA review findings (every state returns to SEARCH, no wedge); timeouts are tunable parameters | active |
| 2026-11-15 | Sonar layout: 2 front, 2 rear, 2 left, 2 right (CAD forward/back + side holders), names front_1..2, rear_1..2, left_1..2, right_1..2; fired one at a time. Supersedes the 4 front + 4 rear rows above (code migrated 2026-11-16, TODO item 10) | Decided by Bryan: sides matter when a skid-steer robot turns in place; exact positions are an assumption until Bryan confirms | active (set by Bryan) |
| 2026-11-16 | Sonar migration: `ultrasonic_logic` exposes `FRONT/REAR/LEFT/RIGHT_NAMES`; behavior uses front_* for slowdown/avoidance, rear_* for RECOVER backing, left_*/right_* only to limit rotation. `BehaviorMachine.step(now, target, front, rear, left=None, right=None)`; missing side lists mean no restriction | Keeps old callers working; one logic path | active |
| 2026-11-16 | Rotation in place (angular != 0 with abs(linear) < 0.02, no arm action) is refused when the sonar on the side being swung into (CCW = left, CW = right) reads below `side_clearance` (0.20 m, working value, TODO: Bryan to tune). In SEARCH the spin direction flips if the other side is clear and the front is not blocked; avoidance turns are zeroed instead of flipped so the robot never turns back into the front obstacle. Both sides close: stands still (SEARCH has no timeout for this; item 15/22 add stale/validity handling) | Skid-steer corners swing sideways; simple and testable | active |
| 2026-11-16 | Sim sonar mounts (`SENSOR_MOUNT`): bearings from the TODO layout table, side sensors staggered +-0.10 m fore/aft, front/rear at robot centre; all sim-only assumptions, not measured | Positions unknown until Bryan sends them | active |
| 2026-11-16 | Bring-up config: `robot.yaml` lists EVERY declared parameter of drive, ultrasonic, arm, gps_imu, detector and behavior (a test fails if a node declares one the yaml lacks, if the yaml has an unknown one, or if an int/float type differs from the node default, which ROS would reject). Top-level keys stay the launch node names (`ultrasonic:` = sonar subsystem). Per-subsystem launch files call `bringup_util.subsystem_launch`; unset markers (-1 pin, 0 number, empty string) are reported by `config_logic.unset_message` | One file for Bryan to edit; reuses existing idle-with-warning behavior of the nodes | active |
| 2026-11-16 | `hardware_check` console script (`hardware_check.py` + pure `hardware_check_logic.py`): per subsystem PASS (all set, no pin problems) / FAIL (unset, invalid or conflicting) / SKIP (nothing filled in yet); exit code 1 on any FAIL | Lets Bryan fill in `robot.yaml` part by part and re-run; SKIP for unassembled parts so the full run is not all red | active |
| 2026-11-16 | Valid pins = BCM 2..27 (Pi 5 header; GPIO0/1 are the HAT ID EEPROM). Pins are checked for duplicates across drive and sonar, and against I2C (GPIO2/3) and GPS UART (GPIO14/15) when the IMU/GPS is configured. A sonar with both pins -1 counts as unused; only one of the two set is FAIL | Header facts, not robot facts. Does not decide the pin budget (blocked on Bryan, item 23) | active |
