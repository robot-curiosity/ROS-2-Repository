# Design Decisions

The agent records design choices here when a TODO item leaves one open
(for example, which ROS message type to use). Bryan can veto any entry:
edit the line or add "VETOED:" and the next agent run will redo that part.

| Date | Decision | Why | Status |
|------|----------|-----|--------|
| 2026-11-13 | Detections stay as JSON in `std_msgs/String` on `/vision/target` (plus `/vision/direction`), now with a `source` field (`yolo`/`gpt4o`) | Existing consumers already use this; vision_msgs is not in the base CI image. Can migrate to `vision_msgs/Detection2DArray` later | active |
| 2026-11-13 | GPT-4o fallback is off by default (`gpt_fallback_enabled`), runs in a background thread, only when YOLO finds nothing or best conf < `gpt_fallback_low_confidence`, at most every `gpt_fallback_interval_seconds`; key only from `OPENAI_API_KEY` env var | Keeps API cost bounded and never blocks the frame loop; no secret in repo | active |
| 2026-11-13 | GPT is asked for normalized 0..1 boxes as JSON; invalid/out-of-range replies are ignored; a reply is trusted for 2x the interval | GPT bounding boxes are approximate, so reject bad data rather than steer on it | active |
| 2026-11-13 | Ultrasonics: one `sensor_msgs/Range` topic per sensor, `/ultrasonic/{front,rear}_{1..4}`, frame `ultrasonic_<name>`; +inf = nothing seen, -inf = too close; 3-sample median filter; reads via `gpiozero.DistanceSensor` (lgpio backend on Pi 5), imported lazily | Standard message type; gpiozero works on Pi 5 with no extra service; per-sensor topics keep nav/behavior code simple. Lives in `trash_vision` package for now so existing CI covers it | active |
| 2026-11-13 | GPIO pins are parameters `trig_pins`/`echo_pins` (8 entries each, order front_1..4, rear_1..4), default -1 = unused; node idles with a warning until set | Pins are unknown hardware facts; TODO: Bryan to fill in | active |
| 2026-11-13 | Drive: `drive` node in `trash_vision`; subscribes `cmd_vel` (`geometry_msgs/Twist`), publishes `odom` (`nav_msgs/Odometry`); no TF broadcast yet (tf2_ros not guaranteed in CI image; add with bringup) | Standard types; keeps CI build safe | active |
| 2026-11-13 | MDD10A driven in PWM+DIR mode via gpiozero (1 kHz PWM); per-wheel PI with feed-forward, accel slew limit, wheel-speed clamp that preserves the arc, `cmd_vel` timeout (0.5 s) stops motors | Simple, safe defaults; logic is pure Python in `drive_logic.py` so CI tests it | active |
| 2026-11-13 | Encoders decoded in software x4 quadrature from gpiozero edge callbacks (A and B both) | No extra library; fine at JGB37-520 speeds. Switch to a pigpio/lgpio hardware counter if ticks are missed | active |
| 2026-11-13 | Pins, `ticks_per_rev`, `wheel_radius_m`, `track_width_m` are parameters defaulting to unset; node idles with a warning (TODO: Bryan to fill in) | Hardware facts unknown | active |
| 2026-11-13 | Arm: `arm` node in `trash_vision`; `std_srvs/Trigger` services `arm/pick`, `arm/deposit`, `arm/stow`; publishes `arm/joint_states` (`sensor_msgs/JointState`) | Standard types, no custom interface package needed in CI. Can migrate to an action later for feedback/cancel | active |
| 2026-11-13 | Pick = fixed waypoint sequence (pre_grasp, grasp, close, lift, stow) with per-step interpolation and joint clamping; success only if gripper stopped open by `grasp_min_gap` | Simple and safe; vision-guided grasp poses can come with the behavior node. Poses are placeholder parameters (TODO: Bryan to calibrate) | active |
| 2026-11-13 | Backend is LeRobot `SO101Follower` (lazy import); empty `port` or failure to open falls back to a dry-run backend that does not move anything | CI/dev without hardware; LeRobot API may differ by version, verify on Pi | active |
| 2026-11-13 | GPS/IMU: one `gps_imu` node in `trash_vision`; publishes `sensor_msgs/NavSatFix` on `gps/fix` and `sensor_msgs/Imu` on `imu/data` | Standard types, no extra CI deps | active |
| 2026-11-13 | GPS read as NMEA over serial (pyserial, lazy import), GGA sentences only with checksum check; covariance estimated from HDOP (HDOP x 2.5 m) | Works with any NMEA GPS module, so the model need not be known | active |
| 2026-11-13 | IMU backend is a model switch `imu_model` (default "" = off); only "bno055" (I2C, NDOF fusion, smbus2 lazy import) is implemented | A concrete model is needed to read registers; BNO055 is a placeholder guess. TODO: Bryan to fill in real IMU model (add a backend if different) | active |
| 2026-11-13 | `gps_port`, `gps_baud`, `imu_model`, `imu_i2c_bus/addr` are parameters; node idles with warnings until set | Hardware facts unknown | active |
| 2026-11-14 | Behavior: `behavior` node + pure `behavior_logic.py` state machine SEARCH -> APPROACH -> PICK -> DEPOSIT -> STOW (+ RECOVER backup after 2 failed picks); reads `/vision/target` JSON and `/ultrasonic/*`, publishes `cmd_vel` and `behavior/state`, calls `arm/pick`, `arm/deposit`, `arm/stow` | Uses existing interfaces; logic testable in CI | active |
| 2026-11-14 | Behavior is disabled by default (`enabled:=false`); pick triggers when target floor-point y >= `pick_floor_y` and centered (TODO: Bryan to calibrate); front sensors assumed ordered left->right (front_1 = left); deposit = `arm/deposit` (bin is on the robot); no GPS navigation, search = spin in place | Safe default; hardware facts unknown | active |
| 2026-11-14 | Obstacle avoidance: stop at `stop_distance` (0.25 m) and turn away from the closer half; linear speed ramps down between `slow_distance` (0.6 m) and stop; backup in RECOVER is blocked by rear sensors | Simple reactive behavior; thresholds are tunable parameters | active |
| 2026-11-14 | Simulation is a lightweight pure-Python 2D kinematic sim (`sim` node, `sim_logic.py`) that replaces drive/ultrasonic/detector/arm (same topics/services), not Gazebo; `sim.launch.py` runs it with `behavior` enabled | Gazebo (ros_gz) is not in the CI image and cannot be tested here; this exercises the real behavior node end-to-end. Gazebo world can be added later | active |
| 2026-11-14 | `bringup.launch.py` starts drive, ultrasonic, detector, arm, gps_imu (each switchable via `use_<node>:=false`) with hardware params from `config/robot.yaml`; `behavior` always started but disabled unless `enable_behavior:=true` | One command on the Pi; unset hardware makes nodes idle instead of fail. yaml values are TODO: Bryan to fill in | active |
| 2026-11-14 | Sim camera/sensor geometry (FOV 1.2 rad, sensor bearings, floor-row model) are invented sim-only constants, not robot facts | Only for exercising logic; real values come from hardware tests | active |
